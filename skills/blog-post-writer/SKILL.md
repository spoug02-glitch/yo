# 정보성 블로그 글 작성

이 스킬의 목적은 두 가지다. **틀린 숫자가 하나도 없는 글**을 쓰는 것, 그리고 그 글이 **AI가 뽑아낸 표 뭉치처럼 읽히지 않게** 하는 것. 두 번째가 없으면 첫 번째는 아무 의미가 없다. 아무도 안 읽으니까.

---

## 0. 작업 순서

1. **목차 먼저 제안한다.** 본문을 바로 쓰지 않는다. 목차를 내놓고 승인을 받은 뒤에 쓴다.
2. 목차 단계에서 **자료 간 충돌이 예상되는 항목을 미리 표시**한다. (예: "유효기간은 자료마다 다름 — 공식 확인 필요")
3. 승인되면 리서치 → 검증 → 집필.
4. 집필 후 **변경·수정 내역을 채팅으로 보고**한다. 파일 안에 자화자찬을 넣지 않는다.

사용자가 "go", "ㅇㅋ", "진행해" 같은 신호를 주면 목차 단계를 건너뛰고 바로 본문으로 간다.

---

## 1. 사실 검증: 1차 자료가 기준

### 우선순위

| 순위 | 자료 | 취급 |
|---|---|---|
| 1 | 발급·주관 기관 공식 사이트, 법령, 공시, 공고 원문 | 기준값. 본문 수치는 여기서만 가져온다 |
| 2 | 언론 보도 | 공식에 없는 사실(도입 사례, 시장 반응)에만 사용. **보도 시점을 반드시 병기** |
| 3 | 블로그·커뮤니티·위키 | 단서 찾는 용도. 본문 수치의 근거로 쓰지 않는다. 불가피하면 "공식 미확인" 표시 |

### 공식 사이트가 안 읽힐 때

요즘 기관 사이트는 대부분 자바스크립트로 화면을 그린다. `web_fetch`를 하면 메타태그만 돌아오고 본문이 비어 있는 경우가 많다. **이때 포기하고 2차 자료로 후퇴하지 말 것.** 브라우저 도구(claude-in-chrome 등)로 실제 페이지를 열어서 읽는다.

- `navigate` → `get_page_text` 조합이 기본
- 메뉴·링크를 못 찾으면 `find`로 링크 목록을 뽑는다
- 아코디언·탭으로 접혀 있는 내용은 `find`로 버튼을 찾아 클릭한 뒤 다시 읽는다
- 그래도 안 열리면 **그 항목은 본문에 쓰지 말고**, "공식 페이지에서 직접 확인하라"고 안내한다

### 같은 사이트 안에서도 대조한다

이게 실전에서 제일 자주 걸린다. 요약 페이지와 상세 페이지의 숫자가 다른 경우가 흔하다. 개편이 부분적으로만 반영됐기 때문이다.

**항목별 상세 페이지가 있으면 반드시 열어서 요약 페이지와 대조한다.** 한쪽만 보고 단정하면 틀린다.

충돌을 발견하면 이렇게 처리한다.

- 양쪽 수치를 **둘 다** 싣는다
- 확인 날짜를 적는다
- 어느 쪽을 기준으로 준비하라고 안내한다 (보통 상세 페이지)
- 어느 쪽이 맞는지 임의로 판단하지 않는다

## 2. 숫자와 출처 규칙

- **추정한 숫자를 그냥 적지 않는다.** 추정이면 "추정치"라고 쓴다.
- 사용자가 주지 않은 내용을 임의로 덧붙이지 않는다.
- 모든 수치에 출처를 붙인다. 본문에서는 `공식 홈페이지 > 자격정보` 처럼 경로 형태로, 전체 URL은 맨 아래 출처 목록에만 모은다.
- 공식이 "미공개"인 항목은 **미공개라고 쓴다.** 인터넷 추정치로 메우지 않는다.
- 언론 보도 인용에는 시점을 넣는다. → *(2025년 7월 보도 기준)*

### 단정 표현 완화

원문이 A라고만 말했는데 B까지 단정하지 않는다.

| 위험한 서술 | 안전한 서술 |
|---|---|
| 국가자격과 동등한 지위를 갖는다 | 법령에 따라 국가·지자체가 우대할 수 있다 |
| 이론 객관식 시험이 아니다 | 별도의 객관식 필기 없이 실기로 진행된다 |
| 서류에서 가산점을 받는 수단이다 | 역량을 보여주는 하나의 평가 요소다 |

## 3. 문체 지침

여기가 이 스킬의 핵심이다. 사실만 맞으면 되는 게 아니다.

### 3-1. 같은 단어를 반복하지 않는다

한 문단 안에서 같은 명사·동사가 두 번 이상 나오면 바꾼다. "확인하세요"가 세 번 나오면 하나는 "챙기세요", 하나는 "짚어보세요"로.

특히 정보성 글에서 닳도록 반복되는 표현을 경계할 것: 확인하다, 제공하다, 활용하다, 진행되다, 구성되다, 다음과 같습니다, ~에 대해, 중요합니다.

### 3-2. 인용구 블록을 쓰지 않는다

`>` 블록인용은 검색 노출에 불리하다. 원문을 그대로 옮겨야 할 때는 **기울임 + 큰따옴표**로 처리한다.

- 쓰지 말 것: `> 국가로부터 인정받은 공인자격이 아닙니다.`
- 쓸 것: *"국가로부터 인정받은 공인자격이 아닙니다."*

주의·경고 박스도 마찬가지다. `>` 대신 **굵은 글씨 리드 문장**이나 짧은 문단으로 바꾼다.

### 3-3. 문단 사이에 관찰 한 줄

글 전체에 **4~5곳** 정도, 정보 전달 사이에 짧은 판단이나 관찰을 끼워 넣는다. 이게 사람이 쓴 글이라는 신호다.

- "이게 실전에서 제일 자주 걸리는 부분이다."
- "총점은 같은데 배점 배분만 다르다. 학습 범위가 뒤집히는 건 아니다."
- "여기서 한 주 차이가 생각보다 크다."

과하면 산만해진다. 4~5곳이 상한선이지 목표치가 아니다.

### 3-4. 표를 한두 군데는 문장으로 푼다

항목이 3개 이하거나, 각 항목의 설명이 한 줄이면 표보다 문장이 낫다. 표가 연달아 세 개 이상 나오면 그중 하나는 반드시 풀어쓴다.

풀어쓴 예시는 `references/style-examples.md` 참고.

### 3-5. 짧은 문단을 섞는다

한두 문장짜리 문단을 글 곳곳에 넣는다. 긴 문단만 이어지면 읽는 사람이 지친다.

특히 중요한 결론 앞뒤에 짧은 문단을 두면 그 문장이 눈에 들어온다.

### 3-6. 서식 규칙 (고정)

발행 서식은 아래로 통일한다. 예외 없음.

| 항목 | 규칙 |
|---|---|
| 폰트 | **나눔고딕** 전체 통일 — 본문·제목·표·캡션 모두 |
| 대제목 (`#`) | 굵게 + 24pt |
| 소제목 (`##`) | **굵게 + 19pt** |
| 하위 소제목 (`###`) | ***이탤릭*** + 본문 크기. 굵게 하지 않는다 |
| 본문 | 15pt |
| 소제목 앞 | **반드시 빈 줄 한 줄**(Enter) 삽입 |

굵기와 이탤릭으로 층위를 가른다. 소제목은 굵게, 하위는 기울여서 시각적으로 구분되게 한다.

이탤릭은 3-2의 원문 인용에도 쓰인다. 헷갈릴 일은 없다. **인용은 큰따옴표를 달고 문단 안에 들어가고, 하위 소제목은 따옴표 없이 한 줄을 혼자 차지**하기 때문이다.

마크다운은 pt 단위와 폰트를 지정하지 못한다. 그래서 결과물을 두 형태로 낸다.

- **`.md`** — 검수·수정용. 소제목은 `##`로 표시하고 앞에 빈 줄을 둔다
- **`.html`** — 발행용. 최상위에 `font-family:'나눔고딕','NanumGothic',sans-serif`를 걸고, `h2`에 `font-size:19pt; font-weight:700`, `h3`에 `font-style:italic; font-weight:400`을 적용

네이버·티스토리 에디터에 붙여넣을 때 HTML 쪽을 쓰면 서식이 그대로 넘어간다. md만 넘기면 에디터에서 일일이 다시 잡아야 하므로 **HTML을 기본 산출물로 함께 낸다.**

집필 중 md 파일에서는 이 형태를 지킨다.

```
...앞 문단의 마지막 줄입니다.
                      ← 빈 줄
## 소제목
본문 첫 줄...
```

### 3-7. 어투 — 글 종류로 가른다

**글을 쓰기 전 `references/voice-profile.md`를 반드시 읽는다.** 사용자 블로그 17편에서 뽑은 실제 문체다.

어투는 두 갈래이며, 글 종류를 먼저 판단해서 고른다.

| 글 종류 | 어투 |
|---|---|
| 경험담·개발기·일상·후기 | **평서체(`~다`)** |
| 정보성 안내·정리글 (자격증·제도 등) | **존댓말** |

가르는 기준은 하나다. **"내가 겪은 일"이 뼈대면 평서체, "독자가 알아야 할 정보"가 뼈대면 존댓말.**

### 3-8. 어투와 무관하게 항상 지킬 것

존댓말로 쓰더라도 아래는 그대로 가져간다. 사용자 글의 리듬은 어투가 아니라 여기서 나온다.

- **한 문장이 한 줄.** 줄 길이 중앙값 23자, 30자 이하가 64.8%. 쉼표로 이어붙일 자리에서 끊어 내린다
- **접속어는 구어 쪽.** 그래서 / 근데 / 그리고. "따라서", "그러므로", "또한"은 쓰지 않는다
- **결론 먼저**, 다룰 내용을 ①②③으로 예고
- **독자에게 말 건다.** "차이가 보이나?", "여기서 하나만 짚고 가자"
- **실패와 한계를 숨기지 않는다.** 매끈하게 다듬지 말 것
- **출처와 기준 시점을 붙인다**
- 헤딩은 질문형이나 구어체를 섞는다. "2. 등급 체계"보다 "2. 나는 어느 등급부터 시작해야 하나"

### 3-9. 쓰지 않는 표현

- `ㅋㅋ`, `ㅡㅡ`, `;;`, `ㅇㅇ` — 사용 금지. 되도록 줄인다
- `총총.` 마무리 — 사용 금지
- 이모지 — 절제. 경고성 표시가 꼭 필요한 곳에만

말줄임표 `…`는 예외로 허용한다.

## 4. 도표 제안

**표가 아니라, 이미지·차트·다이어그램으로 만들면 좋을 지점을 찾아서 사용자에게 알린다.** 자동으로 만들지 말고 목록으로 제안한다.

집필이 끝난 뒤 채팅에서 이렇게 보고한다.

```
## 도표 만들면 좋은 곳

1. [2장 등급 체계] — 등급 로드맵 흐름도
   Future → Junior → Basic → Associate → Professional 을 난이도·대상별로 배치.
   표로는 "어디서 시작해 어디로 가는지"가 안 보임.

2. [6장 시험 일정] — 2026년 연간 캘린더
   회차별 접수기간·시험일·결과발표를 타임라인으로. 온라인/오프라인 마감 차이도 시각화 가능.

3. [4장 출제범위] — 배점 비중 도넛 차트
```

판단 기준: **표로 넣었을 때 "숫자는 보이는데 관계가 안 보이는" 부분**이 도표 후보다. 흐름, 순서, 비중, 시간 축, 분기 구조가 있으면 시각화가 낫다.

## 5. 글 구조 템플릿

고정 틀은 아니지만 정보성 안내글은 대체로 이 순서가 잘 맞는다.

1. 짧은 리드 — 대상 독자, 기준 자료, 확인 날짜
2. 개념과 주관 기관
3. 가장 오해가 잦은 항목 (여기를 앞쪽에 배치할 것)
4. 핵심 스펙 표
5. 선택 가이드 — "나는 뭘 골라야 하나"
6. 상세 정보 (요금·일정·범위)
7. 준비 방법
8. 실익과 한계
9. 체크리스트
10. 마무리
11. 출처 목록 (1차 / 언론 / 2차 구분)
12. 태그

**오해가 잦은 항목을 앞으로 뺀다.** 사람들이 잘못 알고 있는 걸 3번에서 바로잡으면 글의 신뢰도가 초반에 잡힌다.

---

## 6. 출력 형식

- **`.md`(검수용)와 `.html`(발행용) 두 개**를 만들어 `present_files`로 전달한다
- HTML에는 3-6의 서식 규칙(나눔고딕, 소제목 굵게 19pt, 소제목 앞 여백)을 반드시 반영한다
- 채팅 본문에는 파일을 다시 붙여넣지 않는다
- 채팅에는 **① 검증 결과 ② 수정·변경 내역 ③ 도표 제안 ④ 확인 못 한 항목** 만 적는다
- 확인 못 한 항목은 숨기지 말고 명시한다. 이게 신뢰의 핵심이다

---

## 7. 마지막 점검

파일을 넘기기 전에 훑는다. 발행 직전(사람 편집자 시점 리뷰가 필요한 글)이면
`references/editorial-checklist.md`도 함께 통과시킨다 — 제목 과확정, 안전장치
반복, 표 지표 혼동, 개념 설명 과다, 도식 설계 원칙을 다룬다.

- [ ] 폰트가 나눔고딕으로 통일됐는가 (HTML)
- [ ] 소제목(`##`)이 굵게 + 19pt인가 (HTML)
- [ ] 하위 소제목(`###`)이 이탤릭인가, 굵게 처리하지 않았는가
- [ ] 모든 소제목 앞에 빈 줄이 있는가
- [ ] md와 html 두 파일을 모두 냈는가
- [ ] voice-profile.md를 읽고 시작했는가
- [ ] 글 종류에 맞는 어투를 골랐는가 (경험담=평서체 / 정보글=존댓말)
- [ ] ㅋㅋ·ㅡㅡ·;;·"총총."이 들어가지 않았는가
- [ ] 문장이 지나치게 길어지지 않았는가 (한 문장 한 줄)
- [ ] `>` 블록인용이 하나도 없는가
- [ ] 한 문단에서 같은 단어가 반복되지 않는가
- [ ] 관찰·판단 한 줄이 4~5곳 들어갔는가
